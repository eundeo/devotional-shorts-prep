# 제품 요구사항

## 목적

묵상 쇼츠 제작 전 단계를 반복 가능하고 검수 가능한 흐름으로 자동화한다. 제작자는 본문 전문만 입력하고, 담당자는 텔레그램에서 완성된 원고와 예상 이미지 구성을 검토한다. 승인이 확인된 작업만 이미지를 생성한다.

## 선행 조건

- 제작자는 정확한 묵상 본문 전문을 입력할 수 있다.
- 운영자는 전용 텔레그램 봇, 그룹, 승인 담당자를 설정할 수 있다.
- 실행 환경에서 Codex 스킬과 ImageGen을 사용할 수 있다.
- 콘텐츠 제작 방법론은 버전이 부여된 기준 문서로 제공된다.

## 문제 정의

현재 작업은 본문 해설, 묵상 포인트 작성, 오프닝과 썸네일 선정, 스크립트 수정, 이미지 프롬프트 작성, 담당자 보고가 대화 안에서 반복된다. 이 방식은 좋은 결과를 얻을 수 있지만 다음 문제가 있다.

- 제작 규칙을 매번 다시 설명해야 한다.
- 수정 과정에서 이미 확정된 문장이 의도치 않게 바뀔 수 있다.
- 담당자 승인과 실제 이미지 생성 사이에 명시적인 안전장치가 없다.
- 어떤 제작 방식과 리비전으로 결과를 만들었는지 추적하기 어렵다.
- 다른 사용자가 동일한 품질과 흐름을 재현하기 어렵다.

## 사용자와 책임

### 제작자

- 묵상 본문 전문과 선택 지시를 입력한다.
- 생성된 로컬 보고서와 작업 상태를 확인한다.
- `승인 확인`, `보고 재전송`, `작업 상태` 명령을 실행한다.
- 수정 요청이 들어오면 새 리비전 생성을 시작한다.

### 승인 담당자

- 전용 텔레그램 그룹에서 현재 보고 메시지를 검토한다.
- 해당 메시지에 직접 답장하여 승인, 수정 요청 또는 보류 의견을 남긴다.
- 이미지 생성 전에 원고와 이미지 장면 수를 함께 승인한다.

### 외부 사용자

- 공유받은 플러그인을 자신의 Codex 환경에 설치한다.
- 자신의 텔레그램 봇 토큰, 그룹 ID, 승인 담당자 ID를 설정한다.
- 공통 방법론을 그대로 사용하거나 버전을 올려 자신의 운영 규칙을 반영한다.

## 핵심 사용자 시나리오

1. 제작자가 `$devotional-shorts`와 함께 본문 전문을 입력한다.
2. 시스템이 본문을 해설하고 묵상 포인트를 구성한다.
3. 오프닝과 썸네일 후보를 만든 뒤 최종안을 자동 선택한다.
4. 낭독 스크립트와 장면별 이미지 프롬프트를 만든다.
5. 결과를 작업 폴더에 저장하고 담당자에게 텔레그램으로 보고한다.
6. 담당자가 현재 보고 메시지에 답장한다.
7. 제작자가 `승인 확인 [작업 ID]`를 실행한다.
8. 수정 요청이면 변경 범위만 반영한 새 리비전을 보고한다.
9. 승인되면 장면별 이미지를 순차 생성한다.
10. 이미지를 로컬에 저장하고 텔레그램으로 전달한다.

## 확정 요구사항

### 기능 요구사항

| ID | 요구사항 |
| --- | --- |
| FR-01 | 본문 전문만으로 묵상 포인트, 스크립트, 이미지 프롬프트를 생성해야 한다. |
| FR-02 | 본문 위치와 특별 지시는 선택 입력이어야 한다. |
| FR-03 | 실행 시 버전이 지정된 제작 방법론을 자동으로 읽어야 한다. |
| FR-04 | 오프닝과 썸네일 후보를 각각 10개 만든 뒤 최종안 1개와 대안 3개를 제공해야 한다. |
| FR-05 | 고정 순서와 문체 규칙으로 낭독 스크립트를 작성해야 한다. |
| FR-06 | 문장 누적 20자 기준으로 이미지 장면과 프롬프트를 만들어야 한다. |
| FR-07 | 보고서, 상태, 방법론 스냅샷을 작업 ID와 리비전별로 저장해야 한다. |
| FR-08 | 텔레그램에 요약 메시지와 전체 보고서를 전송해야 한다. |
| FR-09 | 현재 보고 메시지에 대한 등록 담당자의 답장만 판정해야 한다. |
| FR-10 | 수정·보류·불명확 응답이 있으면 이미지를 생성하지 않아야 한다. |
| FR-11 | 현재 리비전이 명확히 승인된 경우에만 ImageGen을 실행해야 한다. |
| FR-12 | 생성 이미지를 로컬과 텔레그램 양쪽에 전달해야 한다. |
| FR-13 | 실패 장면만 한 번 재시도하고, 계속 실패하면 검토 필요 상태로 남겨야 한다. |
| FR-14 | 보고 재전송, 승인 확인, 작업 상태 확인을 지원해야 한다. |

### 비기능 요구사항

| ID | 요구사항 |
| --- | --- |
| NFR-01 | 봇 토큰과 실제 사용자 ID를 저장소에 기록하지 않아야 한다. |
| NFR-02 | 동일 작업을 재실행해도 이미 완료한 보고·이미지 작업을 불필요하게 중복 수행하지 않아야 한다. |
| NFR-03 | 작업마다 방법론 버전과 SHA-256 해시를 남겨 결과를 재현할 수 있어야 한다. |
| NFR-04 | 이전 리비전의 보고서와 이미지를 덮어쓰지 않아야 한다. |
| NFR-05 | 플러그인 폴더 단위로 다른 사용자가 설치할 수 있어야 한다. |
| NFR-06 | 텔레그램 연동은 별도 상시 서버 없이 사용자가 실행하는 명령으로 동작해야 한다. |
| NFR-07 | 사람에게 보고되는 실패 원인은 복구 방법과 함께 한국어로 표시해야 한다. |

## v1 범위

- Codex 플러그인과 하나의 핵심 스킬
- 기준 방법론과 승인 예시 관리
- 로컬 파일 기반 작업·리비전 상태
- Python 표준 라이브러리를 이용한 Telegram Bot API 호출
- 사용자가 실행하는 승인 확인 방식
- 승인 후 ImageGen 이미지 생성
- 개인 설치 및 GitHub·압축 파일 공유

## v1 제외 범위

- 웹 관리 화면과 모바일 앱
- 상시 실행 웹 서버와 텔레그램 웹훅
- 관계형 데이터베이스 또는 외부 작업 큐
- 예약 발행과 유튜브 업로드
- 음성 합성, 자막, 영상 편집, 배경음악 합성
- 여러 조직을 동시에 서비스하는 계정·권한 시스템
- 자동 성경 번역문 검색 또는 누락된 장절의 추측

## 보안·재현성·이식성

- 환경변수는 사용자별 로컬 설정에서만 읽는다.
- 보고서에는 텔레그램 토큰이나 승인 담당자의 원시 ID 목록을 출력하지 않는다.
- 승인 판정은 작업 ID, 리비전, 텔레그램 메시지 ID를 모두 비교한다.
- 모든 결과는 방법론 스냅샷과 함께 보관한다.
- 문서와 플러그인 내부 경로는 상대경로를 사용해 사용자 홈 경로에 의존하지 않는다.

## 예외 처리

- 입력 본문이 비어 있으면 작업을 만들지 않고 입력 오류를 반환한다.
- 장절이 없으면 콘텐츠 생성은 계속하되 장절 표기를 추측하지 않는다.
- 텔레그램 설정이 불완전하면 로컬 보고서까지만 보존하고 보고 단계에서 멈춘다.
- 승인 확인이 보고 후 24시간을 넘으면 응답을 승인으로 처리하지 않고 보고 재전송을 요구한다.
- 승인 이후 프롬프트나 스크립트를 수정하면 새 리비전과 새 승인을 요구한다.

## 전체 성공 기준

- 제작자는 본문 전문을 한 번 입력해 담당자 보고까지 완료할 수 있다.
- 담당자는 하나의 보고서에서 묵상 포인트, 원고, 장면 수와 프롬프트를 검토할 수 있다.
- 승인 전에는 이미지 생성 호출이 발생하지 않는다.
- 수정 요청은 이전 리비전을 보존한 새 보고서로 반영된다.
- 승인 후 생성된 정상 이미지는 로컬과 텔레그램에 모두 존재한다.
- 신규 사용자가 자신의 텔레그램 설정만 추가해 같은 흐름을 실행할 수 있다.

## 완료 기준

- 모든 기능·비기능 요구사항이 구현 로드맵 및 테스트 항목과 연결된다.
- v1 포함·제외 범위가 구현 중 추가 해석 없이 구분된다.
- 승인 게이트와 리비전 보존이 핵심 인수 조건으로 명시된다.
