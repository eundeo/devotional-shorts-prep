# 운영 및 배포

## 목적

개인 개발 원본을 안전하게 설치·업데이트하고, 다른 사용자가 자신의 텔레그램 설정으로 동일한 스킬을 사용할 수 있게 한다. 방법론 변경, 작업 복구, 로그 보존, 비밀정보 관리 기준도 함께 정의한다.

## 선행 조건

- [구현 로드맵](08-implementation-roadmap.md)의 1~7단계가 완료되어 있다.
- [테스트 및 인수 계획](09-test-and-acceptance-plan.md)의 출시 전 테스트가 통과한다.
- 플러그인 매니페스트와 스킬 구조가 검증된다.
- 배포물에서 작업 결과와 비밀정보가 제외된다.

## 확정 요구사항

### 개발 원본과 설치본

- 개발 원본은 프로젝트의 `plugins/devotional-shorts-prep/`에서 버전 관리한다.
- 설치본은 사용자의 개인 Codex 플러그인 위치에 둔다.
- 개인 마켓플레이스 항목으로 플러그인 이름, 버전, 소스 경로, 표시 순서를 관리한다.
- 설치본을 직접 수정하지 않는다. 변경은 개발 원본에서 수행하고 검증·재설치한다.
- 캐시된 이전 버전이 사용되지 않도록 업데이트 시 플러그인 개발 절차의 캐시 갱신 및 재설치 단계를 따른다.

### 최초 설치 절차

1. 플러그인 폴더를 GitHub에서 받거나 배포 압축 파일을 해제한다.
2. 매니페스트, 스킬, 참조 문서, 템플릿, 텔레그램 도구의 파일 존재를 확인한다.
3. 개인 Codex 플러그인 위치에 설치하고 개인 마켓플레이스에 등록한다.
4. 실제 값을 넣지 않은 `.env.example`을 참고해 로컬 환경변수를 설정한다.
5. `preflight`로 봇과 그룹 접근을 확인한다.
6. 비운영 테스트 본문으로 로컬 보고서 생성까지 실행한다.
7. 테스트 그룹 보고와 승인 전 이미지 미생성을 확인한다.
8. 승인 후 한 작업의 이미지 전달까지 완료한다.

저장소 배포본은 루트의 `.agents/plugins/marketplace.json`을 비기본 마켓플레이스 `devotional-shorts`로 사용한다. 저장소를 받은 사용자는 다음 공식 명령 순서로 설치한다.

```bash
python3 plugins/devotional-shorts-prep/scripts/validate_architecture.py
python3 plugins/devotional-shorts-prep/scripts/distribution.py audit
codex plugin marketplace add <저장소-루트-또는-owner/repo>
codex plugin add devotional-shorts-prep@devotional-shorts
```

설치 또는 업데이트 뒤에는 기존 작업이 아니라 새 Codex 작업을 시작해 새 스킬을 로드한다. 사용자 전역 개인 마켓플레이스 파일을 직접 편집하지 않는다.

### 다른 사용자에게 공유

지원하는 배포 방식은 두 가지다.

#### GitHub 저장소

- 플러그인 소스, 플러그인 README, 설정 예시, 라이선스와 버전 기록을 포함한다.
- 비밀정보, `jobs/`, 실제 이미지, 비공개 원본 자료는 `.gitignore`와 배포 검사로 제외한다.
- 사용자는 저장소를 받은 뒤 개인 플러그인으로 등록한다.

#### 압축 파일

- GitHub와 같은 플러그인 파일만 포함한다.
- 최상위 폴더 이름은 `devotional-shorts-prep`으로 유지한다.
- 체크섬과 플러그인 버전을 배포 안내에 함께 제공한다.
- 압축 안에 상위 프로젝트의 `docs/`, `jobs/`, `.git`, 로컬 환경설정을 포함하지 않는다.

배포 압축은 다음 명령으로만 만든다.

```bash
python3 plugins/devotional-shorts-prep/scripts/distribution.py build --output-dir <배포-출력-폴더>
python3 plugins/devotional-shorts-prep/scripts/distribution.py verify --archive <배포-ZIP>
```

`build`는 플러그인 ZIP, `<파일명>.zip.sha256`, `marketplace.json`을 함께 만든다. ZIP은 `devotional-shorts-prep/` 하나만 최상위 폴더로 포함한다. 수신자는 체크섬 확인 후 전용 마켓플레이스 루트의 `plugins/`에 압축을 풀고, 동봉한 `marketplace.json`을 그 루트의 `.agents/plugins/marketplace.json`에 둔 다음 해당 루트를 공식 CLI로 등록한다.

배포 검사는 심볼릭 링크, 상위경로 이동, 중복 ZIP 경로, 무결성 해시 불일치, `.env`, `jobs/`, `source-materials/`, Telegram 토큰 형식, 값이 채워진 Telegram 환경변수, 사용자 홈 절대경로를 거부한다. 캐시와 바이트코드만 배포 목록에서 결정적으로 제외한다.

### 사용자별 텔레그램 설정

각 사용자는 자신의 다음 정보를 준비한다.

1. Telegram Bot API 토큰
2. 보고를 받을 전용 그룹 ID
3. 승인 권한을 가진 사용자 ID 목록

설정 후 `preflight`가 성공하기 전에는 실제 보고서를 보내지 않는다. 운영 그룹과 개발 테스트 그룹은 서로 다른 `TELEGRAM_CHAT_ID`를 사용한다.

### 비밀정보 규칙

- 실제 토큰과 ID는 소스, 문서, 예시, 테스트 fixture, 스크린샷에 기록하지 않는다.
- 환경변수 파일을 사용한다면 버전 관리 제외를 확인한다.
- 오류 로그에서 토큰은 앞뒤 일부도 표시하지 않고 전체를 `[REDACTED]`로 대체한다.
- 토큰 노출이 의심되면 즉시 봇 토큰을 폐기·재발급하고 관련 로그와 배포물을 점검한다.
- 다른 사용자에게 설정 파일을 전달하지 않고 변수 이름과 설정 절차만 공유한다.

### 버전 정책

세 종류의 버전을 분리한다.

| 버전 | 형식 | 변경 기준 |
| --- | --- | --- |
| 플러그인 버전 | 의미적 버전 | 기능·도구·설치 패키지 변경 |
| 방법론 버전 | 의미적 버전 | 콘텐츠 생성 규칙 변경 |
| 데이터 스키마 | 양의 정수 | `job.json` 호환 구조 변경 |

방법론 버전은 다음 기준으로 올린다.

- **MAJOR**: 스크립트 고정 구조나 결과 의미가 호환되지 않게 변경
- **MINOR**: 새 생성 규칙, 평가 기준, 선택 섹션 추가로 결과가 달라짐
- **PATCH**: 의미를 바꾸지 않는 표현 명확화와 오탈자 수정

플러그인 버전과 방법론 버전은 같을 필요가 없다. 모든 작업은 두 버전 중 방법론 버전과 해시를 직접 저장한다.

### 제작 방식 업데이트

1. 새 대화, 원고, 담당자 피드백을 `source-materials/`에 원본 자료로 둔다.
2. 반복 가능한 규칙과 특정 작업만의 선호를 구분한다.
3. 반복 규칙만 `references/method.md`에 반영한다.
4. 승인 원고는 생성 이유와 함께 `references/examples.md`에 추가한다.
5. 방법론 변경 수준에 따라 버전을 올린다.
6. 기준 입력 회귀 테스트와 의미 품질 평가를 실행한다.
7. 새 작업에서만 새 버전을 사용한다.

원본 자료는 런타임에서 자동으로 읽지 않는다. 검토되지 않은 자료가 기존 제작 방식에 영향을 주지 않게 한다.

### 기존 작업과 호환성

- 기존 작업은 자신의 `method-snapshot.md`와 저장된 해시를 사용한다.
- 승인 대기 또는 승인 완료 리비전을 새 방법론으로 자동 재생성하지 않는다.
- 새 방법론으로 다시 만들려면 사용자가 새 리비전을 명시적으로 생성하고 다시 승인받는다.
- 데이터 스키마 버전이 현재 도구보다 높으면 쓰기를 거부하고 읽기 가능한 메타데이터만 표시한다.
- 스키마 마이그레이션은 원본 `job.json` 백업을 만든 뒤 별도 명령으로 수행하며 플러그인 시작 시 자동 실행하지 않는다.

### 작업 상태 확인과 복구

`작업 상태 [작업 ID]`는 다음 정보를 표시한다.

- 현재 리비전과 상태
- 방법론 버전
- 보고 전송 시각과 현재 메시지 ID 존재 여부
- 승인 판단과 피드백 요약
- 전체·성공·실패·전달 이미지 수
- 마지막 오류와 권장 복구 명령

상황별 복구 방식은 다음과 같다.

| 상황 | 복구 |
| --- | --- |
| 텔레그램 보고 실패 | 로컬 보고서 확인 후 `보고 재전송` |
| 보고 후 24시간 초과 | 현재 리비전을 재전송하고 새 메시지에 답장 요청 |
| 모호한 답장 | 담당자에게 현재 메시지에 명확히 다시 답장 요청 |
| 이미지 생성 일부 실패 | 프롬프트를 바꾸지 않고 실패 장면만 재개 |
| 이미지 전달만 실패 | 로컬 파일로 실패 장면만 재전송 |
| 데이터 해시 불일치 | 자동 진행 금지, 스냅샷과 이벤트 수동 검토 |
| 프롬프트 수정 필요 | 새 리비전 생성 후 다시 보고·승인 |

### 로그와 작업 보존

- v1은 작업과 이벤트를 자동 삭제하지 않는다.
- `events`에는 상태 변경, 보고, 승인 판정, 생성 시도, 전달 결과를 기록한다.
- 비밀정보와 전체 봇 API 응답은 이벤트에 저장하지 않는다.
- 전달 완료 작업은 운영자가 프로젝트 단위로 백업 또는 보관할 수 있다.
- 90일이 지난 `DELIVERED` 작업은 선택적으로 별도 보관소에 복사할 수 있지만 원본 자동 삭제는 하지 않는다.
- 삭제가 필요하면 플러그인의 자동 동작이 아니라 운영자의 명시적 수동 절차로 수행한다.

### 업데이트 절차

1. 현재 설치본과 플러그인 버전을 기록한다.
2. 개발 원본에서 변경하고 관련 문서를 함께 갱신한다.
3. 정적·단위·통합·회귀 테스트를 실행한다.
4. 플러그인과 방법론 버전을 변경 수준에 맞게 올린다.
5. 개인 설치본을 재설치한다.
6. 새 테스트 작업으로 버전·방법론 해시를 확인한다.
7. 기존 작업이 이전 스냅샷으로 열리는지 확인한다.
8. 배포 변경 기록에 기능, 방법론, 데이터 호환성 영향을 기록한다.

ZIP 설치본은 현재 설치본의 도구로 새 ZIP을 먼저 검증하고 다음처럼 교체한다.

```bash
python3 <현재-설치본>/scripts/distribution.py verify --archive <새-ZIP>
python3 <현재-설치본>/scripts/distribution.py extract --archive <새-ZIP> --destination <마켓플레이스-루트>/plugins --update
codex plugin add devotional-shorts-prep@devotional-shorts
```

`extract --update`는 낮은 버전으로의 덮어쓰기를 거부하고, 새 설치본을 별도 임시 경로에서 검증한 뒤 기존 설치본을 백업 이름으로 이동하고 교체한다. 교체 실패 시 기존 설치본을 복원한다. 같은 버전의 로컬 개발 변경만 `plugin-creator`의 캐시버스터 갱신 절차를 사용한다.

업데이트 실패 시 기존 설치본과 작업 데이터는 변경하지 않는다. 설치본을 되돌려도 `jobs/`는 그대로 유지한다.

## 예외 처리

- 신규 사용자의 Codex 플러그인 위치가 다르면 절대경로를 배포물에 기록하지 않고 해당 환경의 개인 설치 위치를 사용한다.
- 봇 권한이 부족하면 운영 그룹에서 시험하지 않고 테스트 그룹에서 권한을 바로잡는다.
- 데이터 스키마를 읽을 수 없으면 자동 변환이나 덮어쓰기를 하지 않는다.
- 방법론 업데이트가 회귀 기준을 통과하지 못하면 이전 방법론을 계속 배포한다.
- 배포 검사에서 비밀정보 또는 작업 결과가 발견되면 배포를 즉시 중단한다.

## 완료 기준

- 개발 원본과 설치본을 분리해 업데이트할 수 있다.
- GitHub와 압축 파일 모두 비밀정보 없이 배포 가능하다.
- 신규 사용자가 자신의 텔레그램 설정만으로 `preflight`와 종단간 흐름을 완료한다.
- 방법론·플러그인·데이터 버전의 변경 책임이 구분된다.
- 기존 작업은 새 버전 설치 후에도 자신의 방법론 스냅샷으로 재현된다.
- 실패 작업을 정상 결과 손실 없이 상태별 절차로 복구할 수 있다.
