### 작업 데이터·상태

- 작업 ID와 리비전별 `job.json`, `report.md`, 방법론 스냅샷 저장

### Telegram 승인

- 담당자용 요약 메시지와 새 형식의 `report.md` 전송

- 승인, 수정 요청, 보류, 불명확 분류
- `/approve`와 `/approve@봇사용자이름` 명령 지원

### 설치·배포 기반

- 결정적 ZIP, SHA-256, 배포 경계 감사, 검증·원자적 업데이트 도구

## 1.0.0 배포 작업

아래 기술 게이트는 2026-08-13에 모두 통과했다. GitHub 게시 항목만 외부 대상 지정 전이므로 실행하지 않았다.

### 1. 직전 상태 재확인

1. 이 인계 보고서와 세션 09 보고서를 읽는다.
2. `git status`로 사용자 변경과 현재 미추적 파일 범위를 확인한다.
3. 위 네 가지 재검증 명령을 모두 통과시킨다.
4. 실제 비밀정보와 작업 결과가 저장소에 없는지 다시 감사한다.

**게이트:** 69개 테스트, 아키텍처, 배포 감사, 프로젝트 검증이 모두 통과해야 한다.

### 2. 정식 릴리스 메타데이터 정리

1. 기능 변경 없이 v1 완성판을 플러그인 `1.0.0`으로 승격한다.
2. 방법론은 콘텐츠 규칙을 바꾸지 않으므로 `1.1.0`과 기존 해시를 유지한다.
3. 매니페스트, README의 ZIP 예시, 테스트의 버전 의존 부분을 일치시킨다.
4. 배포 대상 라이선스를 확정해 `LICENSE`를 추가한다.
5. `CHANGELOG.md`에 `1.0.0`의 기능, 호환성, 보안, 알려진 범위를 기록한다.

**게이트:** 모든 위치의 플러그인 버전이 `1.0.0`으로 일치하고 방법론·스키마가 불필요하게 변경되지 않아야 한다.

### 3. 최종 소스 검증과 설치 검증

1. 전체 테스트와 정적 계약 검증을 다시 실행한다.
2. 저장소 밖의 새 격리 디렉터리에 `1.0.0` ZIP을 만든다.
3. ZIP과 체크섬을 검증한다.
4. 격리된 마켓플레이스와 격리된 `CODEX_HOME`에 설치한다.
5. 설치 캐시에서 테스트, 아키텍처 검증, 배포 감사를 다시 실행한다.
6. 설치본으로 비운영 본문의 로컬 `DRAFT` 생성까지 확인한다.
7. 실제 Telegram·ImageGen 외부 호출은 신규 배포 검증에 꼭 필요한 경우에만 사용자 승인 후 실행한다.

**게이트:** 개발 원본, ZIP, 설치본의 이름·버전·방법론 해시가 일치해야 한다.

### 4. 버전 관리와 배포 산출물

1. 의도한 프로젝트 파일만 Git에 추가한다.
2. 비밀정보·작업 결과·임시 파일이 스테이징되지 않았는지 확인한다.
3. 첫 릴리스 커밋을 생성한다.
4. 필요하면 사용자가 지정한 GitHub 저장소에 푸시하고 `v1.0.0` 태그·릴리스를 만든다.
5. 릴리스에는 검증된 ZIP, `.zip.sha256`, 설치 안내와 변경 이력을 제공한다.

GitHub 푸시, 공개 범위 결정, 릴리스 생성은 외부 변경이므로 다음 세션에서 사용자의 명시적 대상과 승인을 확인한 뒤 실행한다.

**게이트:** 커밋·태그·릴리스의 소스와 ZIP 체크섬이 동일한 `1.0.0` 원본에서 만들어져야 한다.

### 5. 최종 배포 인수

1. 새 설치 환경에서 `preflight` 전까지 비밀정보가 필요하지 않음을 확인한다.
2. 사용자별 세 환경변수 설정 절차를 README로 재검토한다.
3. 가능하면 기존 설정이 없는 격리 환경 또는 다른 사용자 환경에서 신규 설치 절차를 검증한다.
4. 기존 `0.9.0` 작업이 자신의 방법론 스냅샷으로 열리고 `1.0.0` 설치가 이를 덮어쓰지 않는지 확인한다.
5. 최종 배포 보고서에 설치 위치, 버전, ZIP 해시, 테스트 수, 제한사항을 기록한다.

**게이트:** 신규 설치·기존 작업 호환·비밀정보 비포함을 모두 확인해야 정식 배포 완료로 판정한다.
