# 시스템 경계

이 문서는 `devotional-shorts` 스킬이 로컬 저장, 텔레그램, 승인, 이미지 생성 작업을 조정할 때 지켜야 하는 런타임 계약이다.

## 구성요소 책임

| 구성요소 | 수행 | 금지 |
| --- | --- | --- |
| 스킬 | 입력 해석, 방법론 로드, 콘텐츠 생성, 답장 분류, 승인 게이트 | 비밀정보 저장, 상시 폴링, 전송 성공 추측 |
| 방법론 참조 | 제작 규칙과 승인 예시 제공 | 작업 상태 변경 |
| 보고서 템플릿 | 일관된 검토 구조 제공 | 콘텐츠 선택 |
| 로컬 작업 저장소 | 작업·리비전·스냅샷·이미지 보존 | 중앙 서비스 역할 |
| 텔레그램 스크립트 | 설정 검증, 원시 API 입출력, 메시지·파일 전송, 답장 유효성 검증 | 답장 의미 판정, 이미지 생성 |
| 승인 워크플로 | 유효 답장의 안전 분류·집계, 사용자 승인·상태 명령 | Telegram 원시 HTTP 구현, 이미지 생성 |
| 이미지 워크플로 | 승인 재검증, 시도 예약, 파일 검증·저장, 실패 복구, 전달 완료 조정 | 래스터 생성, 승인 의미 판정, 프롬프트 변경 |
| ImageGen | 승인된 장면 프롬프트로 이미지 생성 | 승인 판정, 원고 변경, 보고서 전송 |

## 저장 경계

- 플러그인 루트에는 배포 가능한 스킬, 참조, 템플릿, 스크립트와 빈 설정 예시만 둔다.
- 작업 결과는 사용자의 현재 프로젝트 `jobs/<job-id>/` 아래에 둔다.
- `method-snapshot.md`, `report.md`, `job.json`, `images/`는 플러그인 설치 폴더에 저장하지 않는다.
- 검토 전 원본 자료는 프로젝트 `source-materials/`에 둘 수 있지만 런타임 방법론으로 자동 사용하지 않는다.
- 상대경로는 현재 프로젝트를 기준으로 저장한다. 특정 사용자의 홈 절대경로를 작업 데이터에 넣지 않는다.
- 콘텐츠 자체 검수, 장면 분할, 보고서 렌더링, 작업 생성과 새 리비전은 `scripts/content_workflow.py`로 수행한다. 이 도구가 내부에서 `scripts/job_store.py`에 위임한다.
- 보고 성공, 승인 판정과 이후 상태 전이는 `scripts/job_store.py`를 통해서만 기록한다.

## 비밀정보 경계

- `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `TELEGRAM_APPROVER_IDS`는 환경변수에서만 읽는다.
- 실제 값을 보고서, 작업 JSON, 오류, 이벤트, 프롬프트 또는 배포물에 기록하지 않는다.
- 텔레그램 도구의 원시 오류에 토큰이 포함될 가능성이 있으면 전체 토큰을 `[REDACTED]`로 바꾼다.

## 작업 흐름

1. 본문 입력을 검증한다.
2. `method.md`를 읽고 버전과 SHA-256을 계산한다.
3. 콘텐츠와 보고서를 현재 프로젝트의 작업 리비전에 먼저 저장한다.
4. 로컬 저장을 다시 읽어 검증한 뒤에만 텔레그램 보고를 요청한다.
5. 텔레그램 도구가 반환한 현재 요약 메시지 ID와 전송 시각을 작업 상태에 저장한다.
6. 승인 확인 요청이 있을 때만 텔레그램 답장을 조회한다.
7. 스킬이 그룹, 답장 대상 메시지, 담당자 허용 목록과 자연어 의미를 판정한다.
8. 현재 리비전이 명확히 승인된 경우에만 이미지 게이트를 검사한다.
9. 이미지를 로컬에 먼저 저장하고 무결성을 확인한 뒤 텔레그램으로 전달한다.

## 작업 라우팅

| 사용자 요청 | 필요한 상태 | 수행 결과 |
| --- | --- | --- |
| 본문 전문 입력 | 없음 | 새 작업의 로컬 초안과 검토 보고서 |
| 원고 수정 | 기존 작업과 피드백 | 이전 리비전을 보존한 새 초안 |
| `보고 재전송 [작업 ID]` | 현재 로컬 보고서 | 새 보고 메시지 ID, 콘텐츠 리비전 유지 |
| `승인 확인 [작업 ID]` | 승인 대기 보고 메시지 | 원시 답장 조회, 분류, 상태 변경 |
| `작업 상태 [작업 ID]` | 기존 작업 | 로컬 상태만 읽어 한국어 요약 |
| 이미지 생성 | 현재 리비전 승인 | 장면별 로컬 이미지와 전달 결과 |

필요한 결정적 스크립트가 설치되어 있지 않으면 해당 외부·파일 작업을 수행한 것으로 보고하지 않는다.

Telegram 명령의 상세 계약은 `references/telegram-contract.md`를 따른다. Telegram 도구는 현재 메시지 직접 답장 여부만 검증하고, 승인 워크플로가 수정·보류·승인·불명확을 집계한다.

### 콘텐츠 워크플로 명령

| 명령 | 용도 |
| --- | --- |
| `segment` | 실제 낭독문을 문장 누적 20자 장면 경계로 계산 |
| `check` | 파일을 만들지 않고 콘텐츠·분량·장면·출처 구조 검수 |
| `create-draft` | 검수·보고서 렌더링·방법론 스냅샷·새 `DRAFT`를 원자적으로 생성 |
| `create-revision` | 보존 범위를 검증하고 이전 결과를 보존한 새 `DRAFT` 생성 |

인수와 생성 JSON 계약은 `references/generation-contract.md`와 `python3 scripts/content_workflow.py <명령> --help`로 확인한다. 제작 작업은 저수준 `job_store.py create-draft`나 `new-revision`을 직접 호출하지 않는다.

### 저수준 작업·상태 명령

| 명령 | 용도 |
| --- | --- |
| `create-draft` | 콘텐츠 워크플로가 검수된 새 작업을 저장할 때 사용하는 내부 명령 |
| `new-revision` | 콘텐츠 워크플로가 검수된 새 리비전을 저장할 때 사용하는 내부 명령 |
| `mark-report-sent` | 실제 보고 성공 메시지 ID를 저장하고 승인 대기 전이 |
| `record-decision` | 현재 보고 메시지에 대한 집계된 승인 결정을 저장 |
| `transition` | 승인 후 이미지 생성 관련 상태 전이 |
| `status` | 현재 작업 상태 요약 읽기 |
| `validate` | 파일·스키마·해시·리비전 일관성 검사 |

각 명령의 인수와 JSON 계약은 `python3 scripts/job_store.py <명령> --help`로 확인한다. 외부 API가 성공하기 전에 성공 상태를 기록하지 않는다.

## 이미지 승인 불변식

ImageGen을 호출하기 직전에 다음 조건이 모두 참이어야 한다.

- 작업 상태가 `APPROVED`다.
- 승인 결정이 명확한 `approved`다.
- 승인 리비전과 현재 리비전이 같다.
- 승인 보고 메시지 ID와 현재 보고 메시지 ID가 같다.
- 승인 이후 스크립트, 장면 수, 프롬프트 해시가 바뀌지 않았다.
- 승인 뒤에 수정 요청 또는 보류 이벤트가 추가되지 않았다.

조건이 하나라도 거짓이거나 확인할 수 없으면 ImageGen 호출 횟수는 0이어야 한다. 승인 이후 콘텐츠가 바뀌면 새 리비전을 만들고 다시 보고한다.

## 실패 경계

- 로컬 저장 실패: 텔레그램에 보내지 않는다.
- 텔레그램 보고 실패: 로컬 결과를 보존하고 재전송 가능 상태를 유지한다.
- 승인 확인 실패: 이미지 생성 상태로 넘어가지 않는다.
- ImageGen 사용 불가: 승인 데이터를 유지하고 이미지 생성 전 상태로 돌아간다.
- 이미지 파일 저장 실패: 해당 이미지를 텔레그램으로 보내지 않는다.
- 데이터와 파일 불일치: 자동 복구하지 않고 `NEEDS_REVIEW`로 남긴다.

## v1 운영 제약

- 웹 서버, 웹훅, 데이터베이스, 외부 작업 큐를 사용하지 않는다.
- 사용자가 명시적으로 승인 확인을 실행할 때만 답장을 조회한다.
- Telegram 봇당 승인 대기 작업은 하나만 허용하며 outgoing webhook이 있는 봇은 사용하지 않는다.
- 여러 실행 장치가 동일 작업 폴더를 동시에 수정하는 방식은 지원하지 않는다.
- 배포물에 `jobs/`, `source-materials/`, 실제 환경설정을 포함하지 않는다.
